# 데이터 러너 첫 버전(튜토리얼 + 1 임무) — 제작 설계

> 원 기획서: `data/data-runner-plan.md`(v0.1). **무엇을 만드는지는 기획서가 기준**이고, 이 문서는 첫 버전을 **어떻게 만드는지**와 기획서에서 달라지는 점만 적는다.
> 표시: **[사용자]** = 사용자가 정함 · **[내 판단]** = 제작자가 정함(사용자 검토 대상) · 표시 없음 = 기획서 그대로.

## 1. 의도와 성공 기준

- 한국과학창의재단과 함께하는 윤리시티(AI윤리교육 게임 10편 중등편) 중 한 편. 학생 시험 플레이는 한참 뒤다. **[사용자]**
- 이번 첫 버전의 성공 = **팀원들이 직접 돌려 보고 "재밌다"고 하는 것.** **[사용자]**
- 그래서 공을 가장 많이 들이는 곳은 **달리기의 손맛**(레인 이동·잡기·퍼펙트·속도감)이다. 검수·감독관·결과 화면은 흐름이 끊기지 않고 기획서의 교육 의도가 전달되는 수준이면 된다. **[내 판단]**

## 2. 목표 / 비목표 / 반목표

**목표**
- 튜토리얼(입양 안내 AI) + 1 임무(침수 판별 AI)를 기획서 §4 흐름 전체로 끝까지 플레이할 수 있다:
  짧은 이야기 → 브리핑 → 달리기 → 검수 → 감독관 질문·승인 → 결과 → (실패 시) 보충 달리기 → 결과 → 마무리 안내.
- PC(키보드)와 태블릿·폰(터치)에서 모두 돈다. 가로·세로 화면 모두.
- 임무 정의(브리핑 장면·조합·카드 흐름·대사)는 코드와 분리된 데이터 파일이다(2~4 임무를 데이터만 바꿔 끼워 넣는 틀).

**비목표(이번에 안 함)**
- 2~4 임무, 선배와의 레이스(고스트), 해커 정체 공개, 동기 성장 서사.
- 완성 일러스트·캐릭터 디자인(러너 디자인은 다른 팀과 맞추는 외부 조건 — 기획서 §12).
- 교사용 화면, 진행 저장·서버 동기화(Firebase 등), 학급 집계.
- "처음 성공 / 보충으로 해결"에 따라 **다음 임무 브리핑 한 줄**이 바뀌는 기능은 다음 임무가 없으므로 기록만 남기고 표시는 안 한다. **[내 판단]**

**반목표(돌아가더라도 이러면 실패)** — 기획서 §0·§10 전부 + 아래
- 판단은 맞았는데 **타이밍 때문에 카드를 놓치는** 달리기(판정 구간이 좁거나 카메라가 카드를 늦게 보여줌).
- 달리기 중 균형 게이지·실시간 알림, 정확도 %, 퍼펙트가 점수·순위·판정에 영향.
- 결과 문구가 AI 탓·플레이어 탓. 지하차도 장면.
- 카드 그림의 화풍·디테일 차이가 정답 단서가 되는 것.

## 3. 만드는 방식

### 3.1 위치와 기술 **[내 판단, 레포 관례를 따름]**
- 레포 `ethicity-games-mid`의 **`/data/`** 폴더(`/privacy/`, `/publicness/` 옆). 작업 브랜치 `data`(워크트리 `D:\Works\ethicity-games-mid-data`).
- **팀원은 `data` 브랜치에서 열어 본다** — 팀은 편마다 브랜치가 지정돼 있다. **[사용자]** main 병합은 팀 피드백 뒤 따로 정한다.
  → 브랜치를 받은 PC에서 **`data/index.html`을 더블클릭(`file://`)해도 그대로 돌아야 한다**: fetch·ES 모듈·외부 이미지 파일 없음(그림은 코드로 생성 — §6), 네트워크 없이 동작. `origin/data`로 push한다(현재 로컬 브랜치의 추적 대상이 origin/main이므로 첫 push 때 `-u origin data`).
- 공공성 편과 같은 결: **빌드 없는 바닐라 JS, 클래식 `<script>` 태그**(ES 모듈 아님), 전역 네임스페이스 `DR`, three.js는 `data/vendor/three.min.js`로 같은 버전을 복사해 둔다.
- 임무 데이터는 `data/missions/tutorial.js`, `data/missions/m1.js`처럼 **`DR.Missions.m1 = {...}` 형태의 JS 데이터 파일**. 기획서는 "JSON 등"이라 했지만, fetch 없이 `file://`로도 열리게 하려고 JS로 감싼다. 내용은 기획서 §9.2 카드 스키마를 따른다.
- 공통 패키지 `shared/ethicity-elementary-common-v1`은 **쓰지 않는다**. 초등편 픽셀 패키지이고, 기존 중등 두 편(privacy·publicness)도 쓰지 않는다.

### 3.2 화면 구성
한 페이지(`data/index.html`) 안에서 화면을 바꿔 끼운다: 타이틀 → 이야기(대화창) → 브리핑 → 달리기 → 검수 → 감독관 → 결과 → 보충 준비(가방 비우기) → 보충 달리기 → 결과 → 마무리 안내. 튜토리얼은 같은 틀을 짧게 쓴다(검수·감독관 단계 생략, 결과는 "귀여운 실패/통과" 한 장).

## 4. 달리기 (가장 공들이는 부분)

### 4.1 시점과 그림 **[사용자: A안]**
- 서브웨이 서퍼처럼 **러너 뒤에서 따라가는 3D 카메라**, 매끈한 3D(three.js). 3레인, 자동 전진.
- ⚠️ **기획서와 달라지는 점**: 기획서 §1은 데이터 세계를 "픽셀 아트"로 정했지만, 사용자가 시안 비교에서 매끈한 3D를 골랐다. 데이터 세계의 **밝은 네온 레트로 분위기**(어두운 남보라 바탕·시안/분홍 네온 선·빛나는 카드)는 유지하고, **픽셀은 카드 썸네일의 자동 픽셀화에만** 남긴다. **[내 판단]** — 기획 팀에 공유가 필요할 수 있다.
- 배경: 네온 격자 도로, 양옆으로 흘러가는 단순한 블록 빌딩 실루엣, 지평선 하늘 그라데이션. 낮은 폴리곤 수로 학교 PC·태블릿에서 60fps를 목표로 한다.
- 러너: 첫 버전은 단순한 3D 인형(캡슐 몸+머리+달리는 팔다리 흔들기). 최종 디자인은 외부 조건.

### 4.2 조작 (기획서 그대로)
- 레인 이동: ←/→, A/D, 좌우 스와이프. 잡기: Space, 화면 탭. 점프 없음.
- 터치에서 스와이프와 탭을 구분: 이동 거리 임계값(초기값 30px) 이상이면 스와이프, 아니면 탭.

### 4.3 카드·판정 구간
- 카드는 레인 위에 세워진 빛나는 패널(썸네일 + 설명표 아이콘 2~3개). 아이콘은 멀리서도 읽히게 크게.
- 카드가 러너 앞 **판정 구간**(초기값: 닿기 0.7초 전부터)에 들어오면 하이라이트, 그때부터 닿기 전까지 잡기를 누르면 잡힌다. 같은 레인의 가장 가까운 하이라이트 카드 하나만 잡힌다.
- **잡기는 "그 레인에 있을 때" 누른 것만 인정**하되, 레인 이동 직후 0.15초 안에 누른 것은 새 레인 기준으로 본다(이동하며 누르는 손 버릇 허용). **[내 판단]**
- 퍼펙트: 닿는 순간 ±0.08초(초기값). 반짝임+효과음만, 기록·판정에 영향 없음.
- 가방이 차면 하이라이트 대신 회색 "가방 가득" 표시, 잡기 무시.
- 판정 구간·속도·퍼펙트 폭 등 손맛 수치는 전부 `data/js/config.js` 한 곳에 모은다(첫 팀 플레이 후 조정).

### 4.4 장애물
- 노이즈 벽(지직거리는 분홍 판). 부딪히면 1초간 속도가 느려지고 화면이 짧게 흔들린다. 잃는 카드 없음.
- 드문 카드는 주로 장애물이 있는 레인 바로 뒤에 놓는다(기획서 §4.2).

### 4.5 손맛 연출 **[내 판단]**
- 레인 이동 시 몸 기울기 + 카메라가 살짝 늦게 따라옴(관성).
- 시간이 갈수록 약간 빨라지는 속도(초기값 시작 대비 +25%까지), 속도선 파티클.
- 잡을 때 카드가 가방 아이콘으로 날아가는 궤적 + 가방 칸 숫자 튐.
- 놓친 카드는 그냥 뒤로 지나감(벌칙 연출 없음 — 놓친 걸 혼내지 않는다).
- 효과음: 잡기·퍼펙트·충돌·이동 정도. Web Audio로 합성(파일 없음). 음소거 버튼.
- 화면 위: 가방 칸 수(예: 12/30)와 남은 거리 막대만. 균형 게이지 없음.
- "움직임 줄이기" 설정(prefers-reduced-motion)이면 흔들림·속도선 끔.

### 4.6 카드 흐름 생성
- 임무 데이터의 비율·장 수(기획서 §7.3: 약 80장, 낮 침수 ~50% / 낮 정상 ~15% / 밤 정상 ~15% / 밤 침수 ~10% / "?" 3장 — 밤 정상·밤 침수 안에 일반 네온 반사·흙빛 카드가 각각 3장 안팎 섞임, §5.4)로 **시드 고정 무작위** 흐름을 만든다. 같은 시드 = 같은 코스(테스트·재현용). 시작마다 시드를 바꿀지는 config 옵션.
- 같은 사진이 반복되는 느낌을 줄이려 카드 종류별로 변형 그림 여러 장(§6)을 돌려 쓴다.
- 달리기 길이: 1 임무 약 3분, 튜토리얼 약 1분 반, 보충 약 30초(기획서 §7.6).

## 5. 검수 · 감독관 · 결과 · 보충

### 5.1 검수 (기획서 §4.3)
- 가방 카드 목록(작은 썸네일 격자). 카드를 누르면 원본 그림을 크게.
- **"?" 카드**: 원본 + 추가 단서(같은 장소 평소 사진·수위 센서 값·촬영 시각·청소차 기록 등 — 기획서 §7.4)를 보고 [침수(깊음)/침수(얕음)/정상(젖음)/정상(마름)] 중 설명표를 붙이거나 **[넣지 않기]**.
- **장면별 현황 요약**: 브리핑 장면 S1~S4 아래에 해당 카드 썸네일을 자동으로 묶어 보여준다. 숫자 충족/미충족 표시는 하지 않는다(체크리스트 게임 방지 — 기획서 원칙 확장). **[내 판단]**
- 카드 빼기는 검수에서도 가능(가방 정리).

### 5.2 감독관 질문
- 대화창 한 장: "브리핑 장면 네 개, 하나씩 다 떠올려 봤어?" → [검수로 돌아가기] / [제출].

### 5.3 결과
- 장면 S1~S4를 하나씩 넘기며 **판정 컷 + 짧은 문구**. 실패 두 종류(불편 / 위험) 구분 — **종류는 장면이 아니라 빠진 조합으로 정한다** **[내 판단]**: 침수 조합(깊은·얕은·흙빛 침수)이 빠지면 "위험"(침수를 안전으로 통과), 정상 조합(마른·젖은·네온 반사 정상)이 빠지면 "불편"(멀쩡한 길을 막음). 둘 다 빠지면 위험을 먼저 보여준다. 감독관이 막아 세우는 컷은 "위험" 실패에 나온다(대표 사례 = S4). 그래서 조합마다 결과 문구 하나("우리가 넣은 데이터에는 ○○가 없었다"), 장면마다 컷은 불편/위험 두 벌.
- 문구는 "우리가 넣은 데이터에는 ○○가 없었다" 형식, % 없음. S4 위험 실패 = 감독관이 막아 세우는 컷 + "승인한 건 나니까, 나도 같이 책임질게."
- 판정 컷 그림은 첫 버전에서 **카드 그림과 같은 절차적 2D 장면 + 간단한 아이콘 연출**(차단봉·우회 화살표·멈춘 차). 사람은 실루엣. 완성 일러스트는 나중. **[내 판단]**
- 1 임무 결과 끝에 선배 한 컷(대사는 기획서 §7.1).

### 5.4 판정 규칙 (기획서 §5·§7.2)
- 순수 함수 모듈 `DR.Judge`(DOM·three.js 무관): 입력 = 제출한 가방 + 임무 데이터, 출력 = 장면별 통과/실패·실패 종류·빠진 조합 → 결과 문구 키.
- 조합당 2장(초기값).
- **경계 조합(S3 '밤·네온 반사 정상', S4 '밤·흙빛 얕은 침수')은 일반 카드로도 채워진다.** **[사용자: (나)]** 흐름에는 설명표가 분명한 **일반 네온 반사·흙빛 카드**가 드물게(주로 장애물 레인) 나오고, 검수에서 **올바르게 분류한 "?" 카드는 2장 몫**으로 센다(기획서 §5 "더 크게 반영"). 그래서 눈 밝은 플레이어는 첫 판에 통과할 수 있고, 놓치면 보충 달리기에서 채운다. 기획서 §7.2의 "경계 조합은 '?' 1장 이상"은 이 규칙으로 바뀐다(§9.2 카드 예시와는 일치).
- 물청소 "?" 카드: 올바르게(정상·젖음) 분류하면 S2 '낮·젖은 정상'을 2장 몫으로 채운다. **[내 판단]**
- 잘못 분류해 넣은 "?" 카드는 조합을 채우지 못하고 결과 문구에서 언급만 한다(기획서 초기 규칙 그대로 — 잘못된 설명표가 해를 끼치는 건 2 임무 주제라 1 임무에서는 무해하게 둔다). **[내 판단]**
- 설계 확인 사례(테스트로 고정): 흔한 카드만 → S2·S3·S4 실패 / 정상 사진만 잔뜩 → **S4 실패**(기획서 §7.5) / 유형마다 똑같이 모으기만 → 경계 카드 없으면 S3·S4 실패 / 빠짐없이 + "?" 올바르게 → 전부 통과. 가방 30칸 안에서 전부 통과가 **가능한지**도 테스트로 확인.

### 5.5 보충 달리기
- 실패 장면을 짚어 주고 → 가방 비우기 화면(가방이 꽉 차 있으면 최소 몇 칸 비워야 출발) → 그 장면에 필요한 카드가 자주 나오는 30초 구간 → 검수("?"가 있으면) → 결과. 보충은 한 번이 기본이고, 그래도 실패하면 한 번 더 할 수 있다. **[내 판단]**

## 6. 그림 (첫 버전) **[내 판단]**
- 기획서 §9.1 권장대로 **2D 레이어 조합을 코드로 그린다**(canvas): 도로·골목·교차로·고가 아래 바탕 몇 종 × 시간대(낮/밤) × 물 높이 레이어(없음/젖음/얕음/깊음) × 흙빛·네온 반사·청소차 물자국 같은 변형 레이어. 모든 카드가 같은 방식이라 화풍이 단서가 되지 않는다.
- "?" 카드의 애매함도 레이어 값으로 만든다(예: 네온 반사 강도를 침수 카드와 비슷하게).
- 썸네일은 원본을 자동 픽셀화. 생성 결과는 첫 실행 때 만들어 캐시(파일 없음).
- 개·고양이(튜토리얼)도 같은 방식의 단순한 2D 그림. 생성형 AI 이미지는 이번에 쓰지 않는다.

## 7. 이야기·인물 (첫 버전)
- 대화창(이름 + 대사, 클릭/Space로 넘김, 건너뛰기 버튼). 인물 이름은 기획서의 가칭 그대로(주인공·동기·감독관·안내 AI·수거봇·선배).
- 초상은 첫 버전에서 색과 모양으로 구분한 단순 아이콘. 안내 AI와 복구 대상 AI는 **확실히 다른 모양**(기획서 §2).
- 대사는 기획서 §6·§7.1에 있는 것을 쓰고, 빈 곳은 제작자가 짧게 채운다(전부 임무 데이터 파일 안 → 기획 팀이 바로 고칠 수 있음).
- 마무리 안내(기획서 §4.7) 한 장.

## 8. 검증
- 단위 테스트(`node --test`): `DR.Judge`(§5.4 설계 확인 사례), 카드 흐름 생성(비율·시드 재현·"?" 3장·드문 카드의 장애물 레인 배치), 잡기 판정(판정 구간·레인 이동 직후 허용·가방 가득).
- 브라우저 확인(공공성 편과 같은 Playwright 방식): 튜토리얼→1 임무→결과→보충까지 자동 진행 1회 무오류, 1366 가로·375 세로 스크린샷 핵심 화면만.
- 손맛은 자동 검증이 안 된다 → **팀원 실제 플레이가 판정 기준**(§1). 보고 때 "자동 확인 / 미확인(손맛·실기기 성능)"을 나눠 적는다.
